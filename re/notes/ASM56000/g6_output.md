# g6_output notes: listing.c, macro.c, object.c, debug.c

Source: `re/out/ASM56000/mod/{listing,macro,object,debug}.c` (Ghidra decompilation, split by
`re/scripts/splitmods.py` using `re/out/ASM56000/modules.txt`), cross-checked against
`re/notes/COFF.md` (from the COFDMP reconstruction) and against the original binary via
`re/scripts/x86dis.py` and live runs of `re/bin_ft/ASM56000.EXE` in
`re/notes/ASM56000/scratch_g6_output/` (files `t1.asm`..`t4.asm` and their `.lst`/`.cln`/`.cld`
outputs, reused from a prior run of this pass; `rd.py` is a tiny helper that reads
strings/words out of the EXE image at a given VA, used throughout this pass).

All function names below use the `lst_`/`mac_`/`ps_`/`dbg_`/`obj_` prefixes; `ps_` = a
pseudo-op handler dispatched directly from the mnemonic table (MACRO/DUP/DUPA/DUPC/PURGE).
Confidence in `g6_output.names.txt` reflects how directly the name is evidenced (error
message text, exact field-offset match against `COFF.md`, or test-file output) vs. inferred
from control flow alone.

**Important address/file-boundary anomaly**: `re/out/ASM56000/mod/macro.c` (as split by
address range from `modules.txt`) begins with three functions — `FUN_0041e8ac`,
`FUN_0041ed0d`, `FUN_0041ed35` (0041e8ac-0041ed62) — that have nothing to do with macros:
they format and sort the "Memory Utilization Report" table rows and are called only from
`lst_print_memory_map` (`FUN_0041e4ac`, in `listing.c`'s own address range, ends exactly at
0041e8ac). The module split is purely address-range based (see BRIEF.md), and this is the one
place in these four modules where the boundary clearly does not follow the original
`listing.c`/`macro.c` file split — the compiler apparently emitted these object-file-local
statics right after `listing.o`'s own functions but the linker (or `modmap.py`'s vote) folded
them into `macro.o`'s span. Since both modules are owned by this group it does not affect any
deliverable; I attributed them to `listing` in `g6_output.names.txt` (their real home) and
flagged it here so whoever eventually assembles `src/asm56000/listing.c` /
`src/asm56000/macro.c` puts them in the right file.

## listing.c — purpose

Owns the listing file (`.lst`): the paginated `lst_line`/`lst_putstr` formatter, page
headers/footers, the post-assembly reports (error/warning summary, `-DSPHOST` symbol dump,
macro table, section table, symbol table + cross-reference, and the memory-utilization map).
It does not own the *source* line/field text it prints (that belongs to `input.c`/`dspasm.c`)
or the running P/X/Y/L counters (owned by `section.c`) — it only formats and paginates them.

### The "126-09-23" date quirk

`lst_print_header` (`FUN_0041cf64`) prints, among other things, two pre-formatted strings —
`&DAT_0045f838` (date) and `&DAT_0045f848` (time) — via `lst_put_field`. Those buffers are
filled once per run by `FUN_00405eea` at **0x00405eea**, which is *outside* listing.c's
address range (it lives in the main/dspasm module, well before `debug.c` starts at 0x40e749)
but is listing.c's only source for "today's date":

```c
local_8 = time(0);
localtime(&local_8);
sprintf(date_buf, "%02d-%02d-%02d", tm.tm_year, tm.tm_mon + 1, tm.tm_mday);
sprintf(time_buf, "%02d-%02d-%02d", tm.tm_hour, tm.tm_min, tm.tm_sec);
```

`tm_year` is `struct tm`'s year-minus-1900 field, and it is used **unmodified** with `%02d`
(no `% 100`, no "+1900"), which is normally harmless (`%02d` doesn't truncate — it's a
*minimum* width) but produces a 3-digit "year" for any date from 2000 onward: for
2026-09-23 the header prints literally `126-09-23` instead of a sensible `26-09-23` or
`2026-09-23`. Every date in `t*.lst` in the scratch directory was produced with
`re/bin_ft/ASM56000.EXE` under `patchtime.py` (fixed clock, year 1999) so it never shows the
bug directly, but the arithmetic is unambiguous from the decompilation and from the `%02d`
format strings at `s__02d__02d__02d_00451a18`/`...28`. **This must be reproduced exactly**
(rebuilt tool prints `tm_year` verbatim, no century correction) for the rebuild's listing
output to match the original byte-for-byte on any date after 1999. Test with `--time` off (or
with `SOURCE_DATE_EPOCH` set to a post-2000 date) and confirm the header shows a 3-digit
"year" whenever the year is >= 2000.

The same two buffers (or the `Opt_portable` flag, see below) also feed the object file's
embedded comment (`obj_write_comment`, `FUN_0042118f`) and the COFF file header's `f_timdat`
— both are covered under object.c's section below.

### Listing line layout (`lst_line`, `FUN_0041bdca`)

One call formats one source-line record. Parameter is the one-character "marker" printed
right after the line number (evidenced by `t1.lst`/`t4.lst`):
- `' '` (space) — normal line
- `'m'` — a line captured verbatim during macro-body/DUP-body capture (`mac_read_body`)
- `'+'` — a line generated by DUP/DUPA/DUPC expansion
- `'d'` (seen via `lst_print_extra_words`) — continuation row printing extra data words of a
  multi-word `DC`/instruction

Column layout, derived from the constant offsets added to the running column cursor in
`lst_line`/`lst_line_cont` and cross-checked against `t1.lst`/`t4.lst`:
- line-number field: `sprintf("%5lu%c%c", line_no, marker, cont_flag)` — 5-digit line number,
  marker char, then either a space or `'+'` (set when `Dup_mem_...`/parallel-move-continuation
  is active) — matches `"    8         P:0000 000000            move..."`.
- fixed column ~10 (`0x1a`/`0x1d`, +6/+4 extra when the memory space is L or LA/LB-sized, i.e.
  `mspace == 0x1c || mspace == 0x11d`, needing 8 hex digits instead of 4): the `P:####`/`X:####`
  address field, printed via `%c:%0*lX` — the space letter comes from `FUN_0043a6c5`
  (space-number → letter, owned by another module) followed by 4 or 8 hex digits of the masked
  address.
- next column (address column + ~10, `+0x10` more if condensed-comment `opt cc` off): the
  6-hex-digit opcode/data word (`obj_stash_listing_word`'s buffer, `Obj_word_buf`), one word
  per call; extra words (2nd, 3rd, ...) of a multi-word instruction/`DC` are printed as their
  own continuation rows by `lst_print_extra_words` with marker `'d'` when `Obj_word_count > 1`
  and `-DSPHOST`/case-comment mode is off.
- (`opt dup`) DUP iteration counter column, if `Lst_show_hex_off`/`Lst_show_float`-style flags
  say a DUP is active: `%5d,  %5ld: ` or `%5d-%5d,  %6ld: ` — `Dup_from`/`Dup_to`/`Dup_incr`.
- (`opt cc`/`Opt_debug_lines`-like flag) buffer usage column: `%2ld`/`%2ld,%2ld` bytes used.
- comment-only fast path when `opt cex`/condensed mode is off and there's no source fields
  left: print `Lst_comment_buf` right-justified at the computed column via
  `lst_print_extra_words`.
- normal path: five source-text fields in fixed column order — label (`0044f810`), opcode
  (`0044f814`), operand (`0044f818`), X-move (`0044f81c`), Y-move (`0044f820`) — each preceded
  by `lst_tab_to(col)` and each column's *width* taken from four globals not owned by this
  module (`Col_opcode`/`Col_operand`/`Col_xmove`/`Col_ymove`/`Col_comment`, i.e.
  `DAT_0044f7f4..0804`, most likely owned by `pseudo.c`'s `OPT`/column-width handling — listing
  only reads them). The comment field (`0044f824`) follows, then continuation data words.

`lst_line_cont` (`FUN_0041c742`) is the same thing minus the address/opcode columns, used for
a line that produced no code (e.g. a label-only or directive-only source line that still needs
its comment printed).

### Page header/footer

`lst_print_header` (`FUN_0041cf64`) prints (once per page, guarded by `DAT_0044f7b8`
"listing enabled"): `Motorola DSP56000 Assembler  Version 6.3.0   <date>` /
`<time>  <source-filename>  Page <n>` / optional title / optional sub-title (set by the
`TITLE`/`SUBTITLE`/`STITLE` pseudo-ops, owned by `pseudo.c`; stored in `Lst_title`/
`Lst_subtitle`). `Lst_page_num` increments once per page. `lst_new_page_header`
(`FUN_0041ce8d`) writes `Lst_header_lines` blank lines first (reserving room for the header
text that's about to be printed — same trick used for the memory-report and symbol-table pages
in `t1.lst`, which all have a blank line then the header at a fixed vertical offset) then calls
`lst_print_header`.

`lst_form_feed` (`FUN_0041cced`, `param_1` = "also start a new page") emits either a literal
form-feed byte (`opt fc`? `DAT_0045eb2c`-driven — this flag is not owned by listing) or
`Lst_page_bottom` (`DAT_0044f7f0`) worth of blank lines to reach the bottom margin, then (if
`param_1`) resets the column/line counters and calls `lst_new_page_header`. `lst_newline`
(`FUN_0041cb65`) is the workhorse: writes one `'\n'`, and once
`Lst_line_on_page >= Lst_page_len` (`Opt`'s `PAGE lines,cols,...`) triggers `lst_form_feed(1)`
instead — i.e. it is the actual pagination trigger, `lst_form_feed` is what performs the
page break.

### `Lst_fp`

`Lst_fp` (`DAT_0045fcac`) is a raw `FILE *`: every write in `lst_putstr`/`lst_newline`/
`lst_left_margin` open-codes `putc()` (`_flsbuf` fast path), i.e. `Lst_fp[0]` = MSVC `FILE._ptr`,
`Lst_fp[1]` = `FILE._cnt`. This matches BRIEF.md's own example original name ("Lst_fp") almost
certainly verbatim.

### Reports (`lst_summary`, `FUN_0041d23b`)

Printed at end of pass 2, in this order: error/warning counts ("N Errors"/"N Warnings"), then
(if `Opt`'s cross-reference-ish flag `DAT_0045ea40` is set) `lst_print_dsphost_syms` /
`lst_print_macro_table` / `lst_print_section_table`, then always `lst_print_symbols` (which
itself does both the plain symbol table and, if enabled, the cross-reference listing), then
(if `DAT_0045ea10`) `lst_print_memory_map`.

- `lst_print_symbols` (`FUN_0041d90d`) walks the symbol hash table (`&DAT_0045fcc0`, 0x3f1
  buckets — owned by `symtab.c`) plus, if "local" symbols are requested, a per-section local
  list (`DAT_0045fc3c`), builds a flat pointer array, sorts it with `lst_cmp_symbol`, then
  prints `Name Type Value Section Attributes` and, separately, the
  `Name / Line number (* is definition)` cross-reference using each symbol's reference list
  (`sym[0x50/4]`, chain via `ref[2]`; `ref[0]` = line number, `ref[1]==1` marks the
  *defining* reference, printed with a trailing `*`).
- `lst_print_memory_map` (`FUN_0041e4ac`) builds a combined list from `Lst_mem_pri_list` +
  `Lst_mem_sec_list` (see `struct mem_node` below), sorts it with `lst_cmp_mem_row`
  (numerically by start address within a memory space), and for each of the six memory-space
  buckets X(1)/Y(2)/L(3)/P(0)/EM(0x1c)/D-DM(0x11d) (skipping EM/D-DM unless the corresponding
  buffer-class counts are non-zero — `DAT_0044f9fc`/`DAT_0044fa00`, not owned here) prints
  `Start  End  Length  Type    Label  Section  Overlay Address`, filling any gap between
  consecutive nodes (or before the first / after the last) with a synthetic `UNUSED` row via
  `lst_print_mem_row(0, ...)`.

## macro.c — purpose

Owns `MACRO`/`ENDM` definition and lookup, dummy-argument parsing and substitution-marker
encoding, `DUP`/`DUPA`/`DUPC` body capture and expansion, `PURGE`, and the macro-library
search path used to auto-`INCLUDE` a macro's source the first time an unknown mnemonic is
used with a library directory configured.

### Structures

**`struct macro_def`** (28 bytes / 7 words, allocated in `ps_macro`):
| word | offset | field | notes |
|---|---|---|---|
| 0 | 0x00 | `char *name` | malloc'd copy |
| 1 | 0x04 | `void *section` | defining section, or the `&DAT_0044f878` "global" sentinel |
| 2 | 0x08 | `long def_line` | source line of the `MACRO` statement |
| 3 | 0x0c | `long argc` | dummy-argument count |
| 4 | 0x10 | `struct mac_arg *args` | dummy-argument list head, or 0 |
| 5 | 0x14 | `struct mac_line *body` | captured body (token list head) |
| 6 | 0x18 | `struct macro_def *next` | singly-linked, head = `Macro_list` |

**`struct mac_arg`** (12 bytes / 3 words — the *dummy*-argument-name list, built by
`mac_parse_args`/`mac_parse_one_arg`): `{ char *name; long index; struct mac_arg *next; }`.
Freed one pointer per node by `mac_free_args` (only `name` is a pointer).

**`struct mac_line`** (12 bytes / 3 words — one captured body line, built by `mac_store_line`):
`{ char *text; char *argmap; struct mac_line *next; }`. `text` holds the line with each
dummy-argument occurrence replaced in place by a 3-byte marker: byte 0 is `\x01` (plain
substitution), `\x02` (the identifier was preceded by `\`, i.e. escaped/backslash form) or
`\x03` (preceded by `?`/`%%`, i.e. the concatenation/stringize form — see
`mac_mark_dummy_ref`, `FUN_0041f58e`); byte 1 is the dummy argument's 1-based index; byte 2 is
set to `\x01` as an end marker. `argmap` is a same-length buffer that is `memset` to 1 over
those 3 marker bytes so the expander can tell a real 3-byte source sequence from the encoded
marker. Freed two pointers per node by `mac_free_body`.

**Value list** (8 bytes / 2 words — actual macro-call arguments *and* `DUP`/`DUPA` per-
iteration substitution values; built by `parse_str_list`, `FUN_00420dc7`, which despite living
in `object.c`'s address range is really macro/DC plumbing — see the object.c section):
`{ char *text; struct value *next; }`. Freed by `free_value_list`.

**Macro-expansion context** (44 bytes / 11 words, allocated by `mac_push_expansion`,
`FUN_00420b7b`, one per active `MACRO`/`DUP`/`DUPA`/`DUPC` invocation, chained on
`Macro_exp_stack`):
| word | offset | field |
|---|---|---|
| 0 | 0x00 | macro/DUP definition pointer (set by caller after the push) |
| 1 | 0x04 | actual-argument count |
| 2 | 0x08 | dummy-argument list being bound (copy of `args`) |
| 3 | 0x0c | (cursor, unused by the functions read here) |
| 4 | 0x10 | first dummy-argument node (`*args`) |
| 5 | 0x14 | actual-argument value-list head (filled per call/iteration) |
| 6 | 0x18 | 0 |
| 7 | 0x1c | call-site source line number |
| 8 | 0x20 | 0 or debug line-number-list snapshot |
| 9 | 0x24 | `Macro_lineno_cur` snapshot, restored on pop |
| 10 | 0x28 | link to the previously active expansion (`Macro_exp_stack` chain) |

`mac_run_expansion` (`FUN_00420cd5`) pushes the frame onto `Macro_exp_stack`, switches the
input-line source to the captured body (calling back into `input.c`, not shown here), resets
per-line listing flags, and on exhaustion pops it and calls `mac_free_expansion`.

### DUP/DUPA/DUPC

All three capture their body the same way (`mac_read_body`, which repeatedly reads a source
line, echoes it to the listing with marker `'m'`, tokenizes it with `mac_scan_line`, and stops
at a matching `ENDM`, tracking nesting via a depth counter that increments on
`MACRO`/`DUP`/`DUPA`/`DUPC` and decrements on `ENDM`), then differ only in how the substitution
*value* list is built and how many times the body is replayed:
- `ps_dup` (`DUP count`): evaluates `count` as an integer expression, replays the body `count`
  times with the loop index as the sole dummy argument's value (formatted `%d`).
  Evidenced in `t1.lst` (`dup 2` → two `nop`s marked `+`).
- `ps_dupa` (`DUPA name,v1,v2,...`): builds the value list directly with `parse_str_list`
  (`v,1,2` → values `"1"`,`"2"`), replays once per value. Evidenced by `t1.asm`/`t1.lst`.
- `ps_dupc` (`DUPC name,'string'`): one iteration per **character** of the string operand.
  Evidenced by `t1.asm`/`t1.lst` (`dupc c,'ab'` → two `dc 'c'` lines).
- `ps_dup_range` (`FUN_004200bc`, unconfirmed mnemonic — candidates: a 4th `DUP` form taking
  `start,end[,increment]`, or possibly `DUPF`) evaluates 2-3 integer expressions and replays
  once per value of a `start..end` (step `increment`, default 1, must be nonzero) loop,
  substituting `%ld` of the current value. Not exercised by any test file in the scratch
  directory; flagged as an open question — whoever names the mnemonic table entry that calls
  it (in `pseudo.c`/`dspasm.c`) should confirm the directive name and update this note.

### Macro library search

`mac_open_library_file` (`FUN_004206ea`) is presumably reached when an unrecognized mnemonic
is encountered and a library search path is configured: it walks `Maclib_path_list`
(`Lst_fp`-independent, a list of directory-prefix strings — populated elsewhere, not in this
module's address range), concatenating each prefix with the macro name and two candidate
extensions, `fopen`s the first hit, and on success pushes an include-file-stack frame (24
bytes: `{ filename, saved_line, nest_id, saved_something, malloc'd copy of the current
source-buffer line, next }`) before switching input to the new file. `mac_lib_recursion_guard`
(`FUN_00420936`) maintains a separate list (`Maclib_guard_list`) of `(name, section)` pairs
currently being searched, to stop the same macro name from re-triggering a library search
while its own library file is still open (returns false / does not open again if already
present).

### Quirks

- Macro body capture always echoes the raw source text to the listing (marker `'m'`) even when
  listing is otherwise disabled (`lst_line` self-gates on the listing-enabled flag, so this is
  harmless, but the echo call happens unconditionally in `mac_read_body`).
- `PURGE` (`ps_purge`) unlinks and frees a `macro_def` node including its body/args, but does
  **not** check whether the macro currently has an active expansion frame on
  `Macro_exp_stack` referencing it — purging a macro from inside its own expansion would free
  memory still in use. Untested; worth a regression test if the rebuild is meant to match
  crash-for-crash as well as output-for-output.

## object.c — purpose

Writes the DSP COFF object file: both the absolute (`.cld`, `F_RELFLG` reversed sense — see
below) and relocatable (`.cln`) forms, using the exact layouts in `re/notes/COFF.md`. This
module only *serializes*; the in-memory section/symbol lists it walks are owned by
`section.c`/`symtab.c`. All multi-byte fields are written big-endian by `obj_fwrite_word`'s
callees (`FUN_0043c450`/`FUN_0043c481`/`FUN_0043c4b2`, all outside this module — the actual
byte-swap primitive is `FUN_0043c4b2(buf, word_size, count)`, called on each staged record
right before the `fwrite`).

### Field-by-field confirmation of `COFF.md`

Every staging buffer object.c fills before writing matches `COFF.md`'s documented offsets
exactly; this cross-check is strong evidence both documents are right, and pins down which
internal counters map to which on-disk field:

**File header** (`Filehdr_stage`, `DAT_00465a40`, written by `obj_write_headers`):
`f_magic=0x2c5` (DSP56000 always, hard-coded), `f_nscns=Sect_count`, `f_timdat` = a
process-start timestamp (`DAT_0045f834`, not owned by this module) **masked to 0 when
`Opt_portable` is set**, `f_symptr=Symtab_ofs`, `f_nsyms=Symtab_count`,
`f_opthdr = Rel_mode ? 0x38 : 0x3c` (confirms `COFF.md`'s "0x38 linker header / 0x3c optional
header" split), `f_flags` assembled bit-by-bit: `F_RELFLG`(1)+`F_EXEC`(2) when absolute and
error-free, `F_LNNO`(4) gated by `Opt_debug_lines`, `F_CC`(0x10000) gated by
`Opt_incremental`, `F_SDI`(0x20000) gated by an SDI-enabled flag plus `Sdi_total != 0`.

**Optional header, absolute file** (`Opthdr_abs_stage`, `DAT_00465b20`, written in
`obj_write_headers` when `!Rel_mode`): `magic=0`, `vstamp=0`,
`tsize = <P-space max addr> - <P-space min addr>`, `dsize = <non-P max> - <non-P min>`,
`bsize=0`, then the five address/mspace pairs (`entry`, `text_start`, `data_start`,
`text_end`, `data_end`) filled from the same min/max-address tracker
(`obj_track_extent`, `FUN_00424050`, and `Cur_file_scope`) that also drives the memory-map
report — `text_start`/`text_end` = P-space extent, `data_start`/`data_end` = the
non-P-space extent, `entry` defaults to the P-space start address unless overridden (by the
`END` operand, tracked in globals outside this module).

**Linker header, relocatable file** (`Opthdr_rel_stage`, `DAT_00465bc0`): `modsize` = computed
total file size (header sizes + `Sect_count*0x34` + `Raw_word_count*4` +
`Reloc_count*0xc` + `Lineno_count*0xc` + `Symtab_count*0x20` + `Strtab_size`), `datasize =
Raw_word_count`, `endstr = 0xffffffff` unless some xref/local-symbol flag is set, `secnt =
Section_def_count+1`, `ctrcnt = Sect_count`, `relocnt = Reloc_count`, `lnocnt = Lineno_count`,
`bufcnt = Buf_count`, `ovlcnt = Ovl_count`, `majver/minver/revno = Obj_majver/Obj_minver/
Obj_revno`, `unused=0`, `sditot = Sdi_total`. This is an exact 1:1 match to `COFF.md`'s field
list and order, confirming that document's layout for this format.

**In-memory section-list node → on-disk section header**: `obj_pack_section_headers`
(`FUN_00421865`) copies a live section struct's first 13 words verbatim (after masking/
recomputing a few) into the 0x34-byte on-disk record — word-for-word the same offsets as
`COFF.md`'s section header table (`s_name`[2], `s_paddr` addr/space[2], `s_vaddr` addr/
space[2], `s_size`[1], `s_scnptr`[1], `s_relptr`[1], `s_lnnoptr`[1], `s_nreloc`[1],
`s_nlnno`[1], `s_flags`[1]). `s_vaddr` defaults equal to `s_paddr` except for `STYP_BLOCK`
sections (flag bit 0x400), where `COFF.md` already documents "the address is the block
length" — confirmed here: `vaddr = old_vaddr - paddr` (i.e. re-purposed as a length) and
`s_vaddr`'s *space* word forced to 4 (N/none). `s_scnptr`/`s_relptr`/`s_lnnoptr` are left 0 for
`DSECT`(1)/`BLOCK`(0x400)/`BSS`(0x80, when neither has raw data) sections, otherwise computed
as running offsets from `Raw_data_ofs`/`Reloc_ofs`/`Lineno_ofs`. The live section struct
itself (its remaining fields past this 13-word prefix, e.g. name/xdef/xref chains) belongs to
`section.c`, not documented here.

**Symbol entry**: `obj_write_symbol` (`FUN_00422b3a`) fills a 0x20-byte staging record
(`Sym_stage`) exactly per `COFF.md`'s symbol-entry table (`n_name` inline if <8 chars else a
string-table offset via the external `strtab_add` helper, `n_value`, mspace, `n_scnum`,
`n_type`, `n_sclass`, `n_numaux`), then (relocatable mode only) one or two 0x20-byte aux
records built from the calling context — a plain "section" aux (`scnlen`/`nreloc`/`nlnno`,
`COFF.md`'s "section aux 0") always, plus a buffer-class aux (`Buf_class`/`Buf_align`/
`Buf_end`... via `Aux_stage`, matching `COFF.md`'s "section aux 1 (new)" layout: `secno`/
`rsecno`/`flags`/`mspace`/`mmap`/`mcntr`/`mclass`) when the symbol names a storage-class
(`BUFFER`) section, or an overlay-form aux when `struct_aux_pending`/overlay data is set. Two
extra one-shot symbols use the same helper: `obj_write_etext_sym` writes an `etext` symbol at
the end-of-text address, and `obj_write_comment` writes the file's opening `GLOBAL`/comment
symbol (assembler name+version+date+object-filename string, see below).

**Aux-entry scope patching**: `obj_patch_endndx` (`FUN_004225ac`) is a single linear pass over
the final symbol table that fills in the `endndx` aux field (`COFF.md`: "C_FCN / C_BLOCK",
"tag", "A_SECT" all have one at offset 0x10) for every open scope — function/block begin
markers (class `0xa`/`0xc`/`0xf`, matching `dbg_scope`'s cases in `debug.c`), struct/union/
enum tags, and `A_SECT`(`0x67`? — the code's numeric class constants for `.text`/`.bss`
section-boundary symbols) — by remembering the most recent open marker of each kind and, on
the next symbol of the same/closing kind (or end of table), writing the current index back
into its aux. It also tracks nested `e`(function)/`d`(block) counters (`Fcn_nest_count`/
`Block_nest_count`, shared with `debug.c`'s `dbg_scope`) to detect true nesting depth for tag
resolution. `obj_reorder_debug_syms` (`FUN_00421e32`) runs first (relocatable mode only) and
physically **moves** groups of symbols so that a struct/union/array tag's member symbols stay
contiguous with their tag record even if `DEF`/`ENDEF` blocks were emitted interleaved with
unrelated code symbols — a stable-partition-style reshuffle keyed off storage class 0x67/200
("A_FILE"/tag-anchor) and 0x65/100 ("function begin" class) boundaries; the exact rule is
intricate (nested loop over aux-count-spanned runs) and is described here at the mechanism
level rather than claimed byte-exact — this is the single most complex function in this
group's modules and deserves its own scratch test (a `.asm` with two interleaved `DEF
STRUCT`/`DEF ARRAY` blocks) before being reimplemented from scratch. `obj_relink_tag_ref`
(`FUN_00422378`) is `obj_reorder_debug_syms`'s helper: after a block moves, it finds the
matching tag/typedef symbol in the *other* half of the table (by scnum-class + old aux tag
index) and rewrites the tag-index aux field to the new position.

### Absolute-file bookkeeping (`obj_file_scope`, `FUN_00423011`)

For `.cld` output only. Pass 1: pushes a 56-byte per-INCLUDE-file node (`Cur_file_scope`
chain) tracking that file's own P-space and non-P-space min/max addresses (fields updated by
`obj_track_extent` whenever `Cur_file_scope` is non-null), used so nested-INCLUDE absolute
output can later emit one `.text`/`.data` symbol *per source file* (each file's block, not
just one for the whole module). Pass 2: instead pops the node and emits exactly that
`.text`/`.data` symbol pair via `obj_write_symbol`. This is the closest thing to a ".file
symbol" object.c produces for absolute output — real `A_FILE`/`.file` debug symbols (name +
`x_ftype`, per `COFF.md`) are emitted by `debug.c`'s `dbg_file`, not here.

### Raw data emission

`obj_emit_word`/`obj_emit_words` (`FUN_004232b6`/`FUN_004238a9`) are the `DC`/single-value-
instruction data-word writers: one or two 24-bit values (dual X/Y move), optionally packed
byte-narrow (when the target memory's word width, `DAT_0045f8bc`, is less than a full DSP
word — e.g. byte- or nibble-addressed peripheral memories) into multiple `obj_fwrite_word`
calls instead of one, and an optional trailing comment string appended to the section's
symbol-table comment aux (`s_BYT_%d_%s` format when byte-packed). Both update
`Raw_word_count`, the running P/non-P address counters via `obj_track_extent`, and stash a
copy of every word into `Obj_word_buf` (`obj_stash_listing_word`) for `lst_line`/
`lst_print_extra_words` to print later — this is the direct object.c → listing.c handoff for
the opcode/data hex dump column.

### Absolute vs relocatable: `Rel_mode`

`Rel_mode` (`DAT_0044f790`) is the global "are we writing a `.cln` (true) or `.cld` (false)"
switch, tested in nearly every function above. Note this is the **inverse** sense of `COFF.md`'s
on-disk `F_RELFLG` bit (`F_RELFLG` = 1 means *absolute*): `Rel_mode` true → optional/linker
header is the 0x38-byte linker form and `F_RELFLG` is left clear; `Rel_mode` false → 0x3c-byte
optional header and `F_RELFLG` set.

## debug.c — purpose

Two mostly-independent responsibilities share this address range: (1) the `BUFFER`-class
storage-block reservation pseudo-op (`dbg_buffer_reserve` and its helpers), which allocates a
matching pair of P-space and data-space (X/Y/L) uninitialized sections; and (2) the `-g`
source-level debug-info state machine (`dbg_directive_dispatch` and its per-sub-directive
handlers), which stages one COFF symbol + aux record per `DEF`/`ENDEF` block for `object.c` to
write out (`obj_write_symbol`). Given the shared naming pattern with `object.c`'s aux-entry
work (`Fcn_nest_count`/`Block_nest_count` used by both `dbg_scope` and `obj_patch_endndx`),
these two are clearly co-designed: debug.c fills the staging aux, object.c serializes and
scope-patches it later, once the whole symbol table is known.

### `DEF`/`ENDEF` state machine

`dbg_directive_dispatch` (`FUN_0040f3e0`) is reached for every debug sub-directive inside a
`DEF ... ENDEF` block (`param_1[1]`'s low byte selects the sub-opcode, 1..0xf); it guards
re-entrancy (`In_def_block`) and dispatches to:

| case | handler | directive (inferred) |
|---|---|---|
| 1 | `dbg_file` | `.FILE`-equivalent — source/include file name + directory |
| 2 | `dbg_set_lineno_aux` | attaches a line number to the pending aux |
| 3 | `dbg_symbol_begin` | `DEF name` — opens the record, looks up/creates the symtab entry |
| 4 | `dbg_symbol_end` | `ENDEF` — finalizes and stages the symbol + aux (see below) |
| 5 | `dbg_symbol_value` | assigns the symbol's value from an expression |
| 6, 7 | `dbg_symbol_attr` | sets storage class (6) / an attribute number (7) from an expression |
| 8 | `dbg_tag` | `TAG name` — struct/union/enum tag name for a pending aggregate |
| 9 | `dbg_size` | `SIZE expr` — aggregate byte size |
| 10 | `dbg_dim` | `DIM expr` — one array dimension (up to 4, `Pending_dim_count`) |
| 0xb-0xe | `dbg_scope` | function/block begin (0xb/0xc) and end (0xd/0xe) markers |
| 0xf | `dbg_line` | standalone `LINE expr` (outside a `DEF` block) |

`dbg_symbol_end` (`FUN_00410100`, the largest function in this group) is where the pending
record actually gets written: it picks the COFF storage class from the accumulated state
(the "e"/"d" nesting counters again decide function vs. block-scope classes), resolves a
pending struct/union tag name back to its defining symbol (linear scan for a matching
tag/size/class), and finally either calls `strtab_add`+`obj_write_symbol`-equivalent output
immediately, or (if the symbol is *new on this pass and the previous pass already staged the
same symbol slot* — the `Symtab_entry == Symtab_saved` check) instead copies the staged 0x20-
byte main record and 0x20-byte aux into two lazily-allocated 32-byte buffers hung off the
existing `symtab.c` entry (`sym[0x54]`/`sym[0x58]`) for `object.c` to pick up later — this is
the two-pass reconciliation that lets debug symbols defined on pass 1 be corrected/finalized
on pass 2 without duplicating them.

### Buffer/storage reservation (`dbg_buffer_reserve`, `FUN_0040e749`)

Implements a "reserve N storage units of a given class/alignment" operation (most likely the
`BUFFER`/`.buffer`-style pseudo-op — the class constants `0x400`/`0x800` match the listing
module's `MOD`/`REV` memory-report labels, see `listing.c`'s memory-map section): validates
the requested class/size combination (class `0x800` requires a power-of-two count; class
`0x400` requires the count to fit `DAT_0044f91c`, an address-mask not owned here), rounds the
byte size up with `next_pow2` when it isn't already a power of two, computes the aligned
P-space and (if a dual X/Y move is active) data-space end addresses, and hands off to
`dbg_open_bss_pair`/`dbg_buffer_close` to actually create the section pair. `Buf_count`
increments once per successful reservation (feeds the linker header's `bufcnt` field in
object.c). `dbg_open_bss_pair`/`dbg_buffer_close`/`dbg_section_note` are read at a coarser
grain than the rest of this module (their exact per-parameter semantics were not individually
verified against a test case) — treat their "med" confidence as "the overall purpose (open/
close a BSS-flagged section pair spanning the reserved storage) is solid, the exact parameter
meanings are best-effort".

### Cross-module interfaces (functions called, not owned by this group)

- `FUN_0042c829` (pseudo.c) — find-or-create the current section descriptor for a given
  memory-space code and flag set; called by `dbg_open_bss_pair`/`obj_emit_words` every time a
  section boundary needs to be (re)opened.
- `FUN_0042447e` (procop.c) — raw "write this 0x20-byte staged symbol/aux record to the object
  file" primitive; every `obj_write_symbol`/`dbg_symbol_end` call ends with one or two calls to
  this.
- `FUN_0042456e` (procop.c) — string-table insert, returns the byte offset (the `strtab_add`
  counterpart of `symtab.c`'s `strtab_lookup`, per `g2_symtab.names.txt`).
- `FUN_0042433e` (procop.c) — records/emits a "current line" debug record outside a `DEF`
  block; called by `dbg_line`, and internally by `obj_emit_words`/`dbg_open_bss_pair` whenever
  a new line's worth of code is about to be written and line-number output is enabled.
  Also called from `dbg_directive_dispatch`'s caller — likely the `LINE` counterpart used
  automatically once per source line, not just via the explicit `LINE` directive.
- `FUN_0042420d` (procop.c) — appends a comment/annotation string to a section or symbol
  record; used by `obj_emit_word`/`obj_emit_words` for the trailing `DC` comment text and by
  `obj_write_comment`.
- `FUN_00410901` (encode.c) — resets/clears the pending `DEF`/`ENDEF` staging state
  (`Sym_stage`/`Aux_stage`-equivalent); called at the start and every early-return of nearly
  every `dbg_*` handler, i.e. it's the "abandon the current debug record" reset.
- `FUN_0043a6c5` (util.c, per `g2_symtab.names.txt`'s sibling modules) — memory-space number
  → one-letter code (`P`/`X`/`Y`/`L`/...), used constantly by `lst_line` and
  `lst_print_symbols`.

## Open questions

1. `ps_dup_range` (`FUN_004200bc`)'s real mnemonic is unconfirmed — see macro.c section.
2. `Opt_portable` (`DAT_0045eb50`)'s real meaning: it simultaneously (a) blanks the listing
   page header's date/version/filename, (b) zeroes the COFF file header's `f_timdat`, and (c)
   substitutes an 8.3-style filename via an external `FUN_00439bd4` helper. This is exactly
   the shape of a reproducible-build knob, but no string evidence (option-letter table) was
   found in `strings.txt` in the time available for this pass; the option letter/mnemonic that
   sets it should be confirmed against `pseudo.c`'s option table before the rebuild relies on
   it for `tests/compare.py --time` reproducibility. Test candidates worth trying:
   `re/bin_ft/ASM56000.EXE -a -b -l t.asm` with various single-letter `OPT`s and compare listing
   headers.
3. `obj_reorder_debug_syms`/`obj_relink_tag_ref` (`FUN_00421e32`/`FUN_00422378`) are described
   at the mechanism level only; a dedicated test source with nested `DEF STRUCT`/array/typedef
   blocks (built with `re/bin_ft/ASM56000.EXE -g`) and a `cofdmp`-style dump of the resulting
   `.cln` symbol table would be needed to pin the exact reordering rule byte-for-byte.
4. Four `DAT_0044f7f4..0804` column-width globals (`Col_opcode`/`Col_operand`/`Col_xmove`/
   `Col_ymove`/`Col_comment`) are read constantly by `lst_line` but never written anywhere in
   this group's four modules — they're almost certainly set by an `OPT`-column-width pseudo-op
   in `pseudo.c`; confirm ownership/name with whichever group covers `pseudo.c`.
